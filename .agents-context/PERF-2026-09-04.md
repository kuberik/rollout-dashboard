# rollout-dashboard performance diagnosis — 2026-09-04

Read-only investigation. No files changed. Live cluster: hub `kind-rollout-prod`
(context `kind-rollout-prod`), spoke `kind-rollout-dev`. Dashboard at
`https://kuberik.192.168.1.102.nip.io`. Fleet at measurement time: 15 Rollouts,
12 Environment objects, 9 Kustomizations, 3 OCIRepositories, 3 RolloutDependencies,
1 cluster reported by `/api/rollouts` in this snapshot (spoke discovery returned no
extra clusters for the unauthenticated request used to sample payload size — see
caveat in B).

**Caveat on live measurements**: this session runs alongside ~90 other concurrently
active QA/UX agents hitting the same hub dashboard (see the `.gstack/browse-network.log`
in this repo, and the roster of `pN-*` agent names in this environment). Several
numbers below (apiserver cumulative counters, page-load cadence mined from the shared
network log) are contaminated by that concurrent traffic and are called out as such.
Where it mattered, I used delta measurements (before/after a controlled burst) instead
of raw cumulative counters, and single-endpoint `curl` timing, which is unaffected by
other tabs.

## Top findings (read this part first)

1. **The premise of the ask is half wrong: this backend already uses the
   controller-runtime `client.Client`, not client-go.** `pkg/kubernetes/client.go:145`
   calls `client.New(config, client.Options{Scheme: scheme})` directly — no
   `Cache`, no `NewManager`, no `SharedInformerFactory`. Controller-runtime's
   client only gets caching when you build it through a `Manager`/`cluster.Cluster`
   and pass `client.Options{Cache: &client.CacheOptions{...}}`; a bare `client.New`
   is a **live, uncached round trip to the apiserver on every single `Get`/`List`**,
   identical in cost to typed client-go. Verified live: 5 requests to `/api/rollouts`
   produced exactly +5 `apiserver_request_total{resource="rollouts",scope="cluster",verb="LIST"}`
   (6398 → 6403, see §B.2). **"Switch to controller-runtime" has already happened and
   bought nothing — the fix is wiring a cache into the client that's already there,
   not swapping libraries.**

2. **A brand-new Kubernetes client (and, worse, a brand-new dynamic RESTMapper) is
   built on every authenticated HTTP request.** `pkg/kubernetes/context.go:21-33`:
   whenever an OIDC token is present (the normal case behind oauth2-proxy —
   `pkg/auth/middleware.go:13-18`), `GetClientFromContext` calls
   `NewClientWithToken(token)`, which runs the **entire** `client.New` construction
   in `pkg/kubernetes/client.go:59-162` — new REST config, new scheme registration,
   new `client.New` (which builds its own dynamic RESTMapper since no `Mapper` is
   passed in `Options`), new `kubernetes.NewForConfig` clientset — from scratch, per
   request. Only the unauthenticated/service-account path (`GetDefaultClient`,
   `context.go:38-43`) is a `sync.Once` singleton. This means a cache sitting behind
   this client would warm up and discard on every request — cache and client
   lifetime must be decoupled from the per-request token before caching helps at all.

3. **`/api/rollouts` (the fleet list) does 8 cluster-wide LISTs per hub request,
   uncached, then fans out over HTTP to every spoke, which does its own 8** —
   `main.go:207-389`, parallelized with `errgroup` (good), but each call is a live
   apiserver round trip. Measured: 855 real page-load samples in the shared network
   log average **288,751 bytes** and 36.6ms server time per `/api/rollouts` call
   (§B.1); confirmed live at 293,060 bytes / ~80ms warm via direct curl.

4. **Three of the eight lists the backend fetches for `/api/rollouts` are computed,
   serialized, and never read.** `imagePolicies`, `imageRepositories`, and
   `ociRepositories` are fetched (`main.go:225-260`) and placed in the JSON response
   (`main.go:369-378`), but `RolloutsListResponse` in
   `frontend/src/lib/api/rollouts.ts:36-52` has no such fields — the frontend
   silently drops them. That's 3 of 8 apiserver LISTs (and their JSON encoding cost)
   spent on bytes nobody reads.

5. **A genuine N+1, twice over, in the single-rollout endpoint.**
   `main.go:435` calls `GetKustomizationsByRolloutAnnotation`, which *internally*
   calls `GetOCIRepositoriesByRolloutAnnotation` (`pkg/kubernetes/client.go:750-771`)
   to build a name-lookup map — and `main.go:444` **also** calls
   `GetOCIRepositoriesByRolloutAnnotation` directly as its own goroutine. Same
   namespace-scoped OCIRepository LIST, done twice, concurrently, on every rollout
   detail page load.

6. **`GetKustomizationManagedResources`** (`pkg/kubernetes/client.go:839-945`) is a
   textbook N+1: 1 GET for the Kustomization, then one GET **per inventory entry**
   (bounded to 8 concurrent via `errgroup.SetLimit(8)`, but still N GETs, not one
   LIST). This is what backs `/api/kustomizations/:ns/:name/managed-resources`,
   called on every rollout detail page load (631 samples in the shared log, avg
   16,080 bytes, 13.1ms — cheap here because the kind cluster is on loopback, would
   scale badly with a remote apiserver or a kustomization with 50+ managed
   resources).

7. **`GetEventsForRollout`** (`pkg/kubernetes/client.go:1422-1546`) is the heaviest
   single call: full namespace-scoped Kustomization LIST → per-kustomization
   `GetKustomizationManagedResources` (the N+1 above, again) → per-Deployment
   ReplicaSet LIST → **one full, unfiltered `Events` LIST per involved namespace**
   (client-side filtered to the last 2 hours and to the objects that matter — the
   apiserver sends every event in the namespace over the wire regardless).

8. **No HTTP caching, no gzip, anywhere.** `main.go:60` is `gin.Default()` — no
   `gin-contrib/gzip`, and no handler sets `Cache-Control`/`ETag` on any JSON route.
   Verified live: `curl -D -` on `/api/rollouts` and `/api/rollouts/:ns/:name` shows
   **no** `Cache-Control`, `ETag`, `Vary`, or `Content-Encoding` header, even with
   `Accept-Encoding: gzip` sent. 293KB travels uncompressed on every poll. (One
   exception: the GitHub `/commits` endpoint deliberately sets
   `Cache-Control: private, max-age=600` for immutable sha↔sha ranges — `main.go`
   commits handler — but that header only helps a browser/CDN cache in front of the
   API; nothing in this stack currently sits there to use it.)

9. **The app-wide poll default is 5 seconds, applied everywhere unless overridden.**
   `frontend/src/routes/+layout.svelte:84-92`: `QueryClient` default
   `staleTime: 1000, refetchInterval: pollWhenHealthy(5000)`. Individual pages then
   layer *more* queries at 5s/10s/15s on top (rollout detail: rollout @5s, full
   fleet list @15s from both `+page.svelte:201` and `+layout.svelte:54`, Navbar
   mounts its own copies of both at `Navbar.svelte:82-96`). TanStack Query dedupes
   identical query keys to the fastest active interval, so this is not literally
   N× the network traffic, but it does mean the fleet-wide `/api/rollouts` — the
   288KB response — is being polled by *every open tab* every 5-15 seconds even
   when nothing has changed, with no ETag/304 path to make a no-op poll cheap.

10. **GitHub calls already have real engineering behind them and are not the
    live problem the task brief assumed.** The task prompt described "a 401 on
    `/commits` on every rollout page load" as if unresolved; the code
    (`frontend/src/lib/components/CommitSummary.svelte:86-100`,
    `frontend/src/lib/api/errors.ts`) shows this was already fixed on 2026-09-0x:
    `isRetryable` never retries 401/404, and a previously-measured "140 failed
    `/commits` requests a minute" storm was traced to `refetchInterval` polling an
    auth failure and closed. What's *still* true: each `CommitSummary` instance and
    each rollout row still fires its own `/commits` (and `/api/auth/github/status`)
    request rather than checking a single shared "GitHub not connected" flag first
    — 769 `/api/auth/github/status` calls and comparable `/commits` calls appear in
    the shared network log, proportional to page loads (§B.1). It's a real but
    smaller "eliminate the call when unconfigured" win, not a retry storm.

## A. How the backend serves each request

### A.1 Client type, caching, fan-out mechanism

- **Client**: `sigs.k8s.io/controller-runtime/pkg/client`, constructed by
  `client.New` — `pkg/kubernetes/client.go:145-150`. **No cache/informers.** No
  `Manager`, no `cluster.New`, no `client.Options.Cache`. Every `Get`/`List` is a
  synchronous HTTP round trip to whichever apiserver `config.Host` points at.
- **Two client lifetimes coexist**:
  - `GetDefaultClient()` (`pkg/kubernetes/context.go:36-43`) — `sync.Once`
    singleton, service-account credentials, reused for the process lifetime. Used
    when no OIDC token is present (e.g. this investigation's unauthenticated
    curl probes).
  - `GetClientFromContext(c)` (`pkg/kubernetes/context.go:21-33`) — when an OIDC
    bearer token is present (the normal authenticated browser session, injected
    by oauth2-proxy per `pkg/auth/middleware.go:13-18`), calls
    `NewClientWithToken(token)`, which reruns **all** of `NewClientWithToken`
    (`pkg/kubernetes/client.go:59-162`): rebuilds `rest.Config`, re-registers 8
    scheme groups, calls `client.New` (which internally builds a *fresh dynamic
    RESTMapper* since `Options.Mapper` is never set), and calls
    `kubernetes.NewForConfig`. **This runs once per HTTP request** for every
    logged-in user. Confirmed by code path; timing impact on this specific kind
    cluster is small (apiserver on loopback, RESTMapper discovery is fast against
    a handful of CRDs) but the construction cost — and, more importantly, any
    future cache's warm-up cost — does not amortize across requests.
- **Multi-cluster fan-out**: NOT done via a multi-cluster controller-runtime
  client. The hub dashboard, after answering its own local queries, makes an
  **HTTP call to each spoke dashboard's own `/api/rollouts` endpoint**
  (`main_fanout.go`, `fanOutRollouts` / `discoverClusters`), guarded by an
  `X-Kuberik-Fanout` header so a spoke doesn't fan out again
  (`main_fanout.go:33-36`). So each spoke independently repeats its own 8-LIST
  fan-out for every hub-initiated request. This is a legitimate design for a
  pull-based, no-inbound-cluster-calls architecture (`cloud`'s constraint doesn't
  strictly apply to rollout-dashboard, but the same principle holds here — the hub
  calls out to spokes over HTTP, never the reverse), but it means the "8 LISTs"
  cost below applies *per cluster*, sequenced by one outer HTTP hop.

Fleet-wide cost estimate for the live fleet (15 rollouts, 9 kustomizations, 2
clusters): one `/` page load = 8 LISTs (hub) + 1 HTTP hop + 8 LISTs (spoke) = **16

page load = 7 parallel K8s ops just for the base payload, then the page's other
components (health-checks, events, schedules, managed-resources, permissions) add
roughly 6-8 more requests, several of which are themselves multi-call fan-outs
(events being the worst: LIST → N managed-resource fan-outs → LIST → per-namespace
Events LIST).

### A.3 GitHub

- `pkg/githubcache/cache.go` — HTTP-layer cache built on `github.com/cjwagner/httpcache`
  (same library `environment-controller` uses via prow's `ghcache`), **partitioned
  by `Authorization` header** (so one user's cached bytes can never leak to
  another — `cache.go:20-25`), sitting *under* the auth round-tripper so the
  partition key is the final bearer token. `no-cache` (always revalidate via
  ETag/If-None-Match, cheap 304 that doesn't spend rate-limit budget) is the
  default for everything mutable; a real TTL (`ImmutableTTL`) is granted **only**
  for sha↔sha compare ranges, which cannot change (`cache.go:34-47`).
- `/commits` (`main.go` commits handler): requires a per-user GitHub cookie
  (`readCookie(c, githubTokenCookie)`); if absent, returns
  `401 {"error": "github_not_connected"}` immediately — no retry loop (fixed,
  see top finding #10). Sets `Cache-Control: private, max-age=600` for immutable
  ranges, `no-store` otherwise.
- **Still true**: nothing gates the *client* from firing the request in the first
  place when GitHub isn't connected — each `CommitSummary` instance and the
  `/api/auth/github/status` check both fire independently per component mount.
  769 status-check calls appear in the shared network log, each ~37 bytes/~7ms —
  cheap per call, but N-per-page-load with no shared "connected: false, stop
  asking" cache above the query layer.

### B.2 Kubernetes API call counts (delta method)

Cumulative `apiserver_request_total` counters were contaminated by ~5.8 days of
uptime and concurrent controller reconciliation + other agents' traffic, so I
used before/after deltas around a controlled burst instead:

```
before: apiserver_request_total{...,resource="rollouts",scope="cluster",verb="LIST"} = 6398
5× curl https://kuberik.192.168.1.102.nip.io/api/rollouts
after:  apiserver_request_total{...,resource="rollouts",scope="cluster",verb="LIST"} = 6403
```

**+5 for +5 requests, exactly 1:1** — confirms zero caching: every dashboard
request is a fresh Rollouts LIST against the apiserver, with the same pattern
holding (by code inspection, A.2) for the other 7 lists on `/api/rollouts` and
every list-then-filter call elsewhere. No informer, no request coalescing, no
short-lived response cache.

### B.5 Where the time goes

At current fleet scale (15 rollouts, loopback apiserver), **the apiserver itself
is not the bottleneck** — 30-40ms server time for the heaviest call
(`/api/rollouts`, 8 parallel LISTs). The measured cost is almost entirely
**bytes on the wire** (293KB uncompressed, no ETag/304 path, re-sent in full every
5-15s per open tab) and **call count against a hypothetical remote spoke** — the
call graph in A.2 is the real risk surface, because every one of those LISTs
becomes a network-latency-bound round trip the moment the spoke apiserver isn't
on the same loopback interface as the hub. This is exactly the situation the live
hub/spoke topology already has today (hub `kind-rollout-prod` calling spoke
`kind-rollout-dev` over the host network) — worth re-measuring the fan-out leg
specifically, e.g. `curl` timing `/api/rollouts` on the hub vs. directly on the
spoke, to see the marginal cost of one extra network hop, which I did not have
time to isolate cleanly given the concurrent traffic on this shared environment.

## C. Ranked proposal (impact ÷ effort)

### 1. Wire a cache into the client that's already controller-runtime — **High impact, Medium effort**
The client is already `sigs.k8s.io/controller-runtime/pkg/client`; the fix is
building it through a `cluster.New(config, cluster.Options{...})` (or a full
`manager.New` if lifecycle hooks are wanted) with `cache.Options` scoping
informers to the CRDs and namespaces the dashboard actually reads — Rollout,
Kustomization, OCIRepository, Environment, KruiseRollout, RolloutDependency,
RolloutGate, RolloutSchedule/ClusterRolloutSchedule, HealthCheck. **What it
fixes**: turns every `/api/rollouts` LIST from a live apiserver round trip into
an in-memory read against a synced informer cache — the +5-for-5 delta in §B.2
goes to +0 for reads between watch events. Cuts apiserver LIST volume for the
whole fleet from "1 per open tab per poll interval" to "1 per resource type per
process lifetime plus incremental watches." **What it costs**:
  - **The per-request-client problem (finding #2) must be fixed first, or this
    buys nothing.** A cache built inside `NewClientWithToken`, torn down every
    request, never gets to serve a second read from itself. The cache has to be
    long-lived (built once at startup, or once per distinct token/identity with
    real TTL-based reuse), which is the real prerequisite work here — not the
    cache itself.
  - **RBAC scoping**: this dashboard authenticates per-user via OIDC specifically
    so kubectl-equivalent RBAC applies per operator. A single shared informer
    cache is built under ONE identity (typically a service account with broad
    read access) — reads served from it bypass the viewing user's own RBAC unless
    a separate authorization check is added on top of every cache read. This is
    the load-bearing design question before touching code: either (a) keep the
    cache scoped to the default/service-account client only, and continue doing
    live, per-user-token reads for anything gated by fine-grained RBAC (most
    reads here are coarse "can view this namespace" which the frontend already
    gates via `permissions/all`, so this may be acceptable), or (b) run a cache
    per-identity, which multiplies memory by concurrent distinct users and
    reintroduces most of the warm-up cost this is meant to avoid.
  - Memory: 9 resource types × 2 clusters, full-fleet scale (15 rollouts today,
    unknown ceiling) — trivially small at current scale, needs a number before
    scaling further.
  - Startup warm-up: first LIST+WATCH per resource type still costs a full LIST;
    fine for a long-lived pod, bad for the "shared kind cluster with a container
    restart loop" failure mode this repo's own `ENVIRONMENT.md` already warns
    about.
  - Spoke watches over the network: if extended to spoke resources (it shouldn't
    be — spokes are reached over the existing HTTP fan-out, not a second informer
    watching a remote apiserver directly) this reintroduces exactly the kind of
    inbound-to-cluster assumption this product's pull-based sibling (`cloud`)
    explicitly forbids. Scope the cache to **hub-local resources only**; leave the
    spoke fan-out as HTTP calls to the spoke's own (now also cached) `/api/rollouts`.
  - **A plain `client-go SharedInformerFactory` would do the same job for
    less** — this codebase already imports `client-go` for the `Clientset` (pod
    logs), and everything read here is typed (no unstructured watches needed
    except the small `GetKustomizationManagedResources` fan-out). A
    `SharedInformerFactory` per typed group avoids controller-runtime's generic
    dynamic-client machinery and its RESTMapper-per-client-construction cost
    (finding #2) entirely. Recommend evaluating this over `cluster.New` unless
    the team wants controller-runtime's `Manager` for other reasons (leader
    election, webhooks — none of which this dashboard needs).
  - **Measure after**: repeat §B.2's delta test — a 5-request burst to
    `/api/rollouts` should show ~0 delta in `apiserver_request_total` LIST count
    (module a periodic re-list on watch bookmark expiry).

### 2. Fix the per-request client construction — **High impact, Small-Medium effort, do this FIRST**
Decouple the OIDC-token-scoped **authorization check** from the **long-lived read
client**. Concretely: keep a single long-lived cached client (service-account or
a narrow read-only identity) for all LIST/GET reads, and use the per-user OIDC
token *only* for the `SelfSubjectAccessReview` calls (`/permissions/all`) and any
write path (pin, bypass-gates, force-deploy, etc.) that must be attributed to and
authorized as the actual operator. This is the prerequisite for #1 to have any
effect, and on its own removes one full `client.New` (scheme registration + fresh
dynamic RESTMapper construction + new clientset) per authenticated HTTP request.
**Effort**: touches `pkg/kubernetes/context.go` and every write handler that
currently assumes `GetClientFromContext` gives it a request-scoped, correctly-
authorized client — needs care that write paths keep using the real user's
token (never silently downgrade a mutating call to the shared service account).
**Measure after**: time-to-first-byte on `/api/rollouts` for an authenticated
session, compared to the unauthenticated baseline in §B.1 (currently expected to
be measurably slower per finding #2, though small on loopback — worth confirming
with an actual OIDC session rather than the unauthenticated curl used here).

### 3. Eliminate the concrete N+1s found in A.2 — **Medium impact, Small effort**
- Drop the duplicate OCIRepositories LIST in the rollout-detail handler
  (`main.go:435` vs `main.go:444` — have the standalone goroutine reuse the
  kustomization goroutine's result, or vice versa). One-line-scale fix, cuts one
  full namespace LIST off every rollout detail page load.
- `GetKustomizationManagedResources` (`client.go:839-945`): batch the inventory
  GETs by GVK+namespace into LISTs with a field/label selector where the CRD
  supports it, instead of one GET per entry. Where that's not possible (mixed
  GVKs in one inventory), keep the bounded-concurrency fan-out but cap it
  proportional to inventory size properly (already at 8, fine) — the bigger win
  is reusing the *already-fetched* managed-resources for `GetEventsForRollout`
  instead of re-deriving them (see below).
- `GetEventsForRollout` (`client.go:1422-1546`) re-derives the same managed-
  resource walk that the `/managed-resources` endpoint just computed, and both
  fire on the same page load (per §B.1, both average 13-26ms and both appear
  600+ times in the shared log). Cache the managed-resources result per
  kustomization for the lifetime of one request (or share it via the existing
  `errgroup` if these ever get merged into one handler), and switch the
  per-namespace Events LIST to a field-selector query
  (`involvedObject.name=...`) or at minimum stop pulling the *entire* namespace's
  events when the interesting set is a handful of Deployments/ReplicaSets.

### 4. Aggregate the rollout-detail page into fewer round trips — **Medium impact, Medium effort**
The rollout detail page currently issues, across the components that mount on
it, ~8 separate requests (rollout, health-checks, events, schedules,
managed-resources, permissions, rollout-tests, commits). Several of these
(health-checks, schedules, rollout-tests) are already namespace-scoped
list-then-filter calls that could be answered as extra fields on the main
`/api/rollouts/:ns/:name` response for near-zero extra apiserver cost (they're
already parallel goroutines in that handler's `errgroup` — extending the
`gin.H{...}` response with 2-3 more fields is a small addition once the cache
in #1 makes the extra LISTs cheap). This is a frontend-breaking response-shape
change — flag loudly and coordinate with whoever owns `frontend/src/routes/rollouts/[cluster]/[namespace]/[name]/+page.svelte` and its sibling components before landing.

### 5. HTTP caching (ETag/304) + gzip — **Medium impact, Small effort, do this early**
Two independent, low-risk, high-ratio wins:
- Add `gin-contrib/gzip` (one line in `main.go` near `gin.Default()`). 293KB → an
  order of magnitude smaller on the wire for `/api/rollouts`; zero behavior
  change, zero frontend impact.
- Add `ETag`/`If-None-Match` on the two heaviest GET endpoints
  (`/api/rollouts`, `/api/rollouts/:ns/:name`) computed from a hash of the
  response body (or, once #1's cache exists, from the informer's resource
  version) — turns a same-data poll into a 304 with an empty body. This directly
  cuts the "every open tab re-sends 293KB every 5-15s" cost from finding #9.
  **Not a frontend-breaking change** if done as a pure `Cache-Control`/`ETag`
  addition — TanStack Query doesn't currently send conditional headers itself,
  so the immediate win is bandwidth on the response, not fewer requests; pairing
  with #6's `staleTime` tuning is what reduces request *count*.

### 6. Push instead of poll — **High impact, Large effort**
The dashboard already has one correctly-modeled push mechanism (pod logs via
SSE, `logs.ts`). Extending that pattern — a watch-driven SSE/WebSocket channel
that tells the frontend "the fleet changed, refetch now" instead of blind 5-15s
polling — is the highest-ceiling fix for request *count*, but is genuinely large:
needs the cache/informers from #1 as a source of change events, a new
long-lived connection type per browser tab, and reconnection/backoff handling
on both ends. Correctly sequenced *after* #1, not before — there's no watch
stream to drive it from otherwise. Recommend as a follow-up quarter, not this
week.

### 7. Frontend cadence tuning — **Small-Medium impact, Small effort**
Independent of the backend work: raise `staleTime` on the fleet-list query
(currently effectively 1s app-wide, overridden per-page to 10-15s — could go
higher, e.g. 30s, given the fleet doesn't change every few seconds in practice),
and add `refetchOnWindowFocus`/hidden-tab gating if not already present (spot
check: `+layout.svelte:88` already sets `refetchOnWindowFocus: false` globally,
good). This is cheap to try and cheap to revert; the constraint is UX (staler
data on screen), not engineering risk.

### 8. Eliminate GitHub calls when unconfigured/unauthenticated — **Small impact, Small effort**
Gate `CommitSummary`'s query and the per-row `/commits` fetch behind a single
shared `githubStatus.connected` check fetched once (already exists as
`fetchGithubStatus`/`GithubStatus` in `github.ts:180-188`) instead of letting
every row independently discover "not connected" via its own 401. Small win
(37B/~7ms per call today, per §B.1) but easy and removes noise from server logs.

### 9. Payload trimming — **Small impact, Medium effort**
Drop the 3 unread lists from `/api/rollouts` (imagePolicies, imageRepositories,
ociRepositories — finding #4) — pure backend change, **zero frontend risk**
since `RolloutsListResponse` never declared them. Beyond that, trimming CRD
`status`/`spec` fields into purpose-built DTOs is real but lower priority than
gzip (#5) for the same byte-reduction goal with far less risk of breaking a
frontend field it turns out something does read.

## Slice 3 follow-ups — landed 2026-09-04 (cadence residue, measured on my own timeline)
After slice 3 the rollout Overview still made ~69 requests/min. Three separate causes, each measured
with a from-load timeline of every `/api/*` response (`waitUntil: 'load'`, then a fixed window):
1. **Page-level overrides ignored the stream** (0ce2d21): every `pollWhenHealthy(N)` / `staleTime: N`
   override on the fleet list, rollout detail, schedules and Navbar now takes the two-argument form, so
   nothing polls faster than once a minute while the stream is healthy and the old cadence returns
   within one interval when it drops (verified by aborting the stream route). Two GitHub-status queries
   that inherited the fast default no longer poll. Bug fixed on the way: cluster-scoped
   RolloutSchedule events carry no namespace and were dropped by the namespace guard.
2. **Invalidation was kind-blind** (9c305ee): every batch invalidated the fleet list and every
   rollout-scoped key in the namespace, including the per-user `permissions/all` SSAR; a HealthCheck
   probe writing its status every ~30 s refetched seven queries. The map is now per kind (Rollout →
   fleet + its own rollout query; HealthCheck → health-check queries in the namespace only;
   Kustomization → fleet + the managed-resources queries naming it; schedules → schedule queries;
   permissions never). Pin / clear pin on the hub-local prod rollout through the UI reflected on the
   Overview, `/` and `/rollouts` in 0.1–0.3 s.
3. **The stream's headers arrived ~10 s late through the proxies** (cdee6a0): request at 0.4 s, headers
   at 10.9 s, because a proxy on the path (Envoy gateway, vite) holds a headers-only chunked response
   until the first body byte (1 ms straight at the pod). Until then the client counted the stream as
   down and every query polled at the 5 s stream-down cadence: three full refetch rounds per page
   load. The handler now writes `retry: 5000` and an SSE comment line at connect; headers arrive at
   0.5 s and the rounds are gone.

Measured after the three: `/` ≈ 3.3 requests/min. Rollout Overview steady state ≈ 15–18/min, and the
timeline shows what it is: every ~30 s a HealthCheck probe write, then two Rollout status writes one
second apart, each refetching the rollout and the fleet list. `kubectl get rollout -w` diffs show those
Rollout writes change nothing but the ORDER of `status.gates[]` — the rollout-controller rebuilds the
list from a cached LIST whose order is a map walk, so every reconcile writes a status that differs
only in order (generation unchanged). That is churn on etcd and every watcher, not a dashboard
problem; the fix is a deterministic sort in the controller (in progress). The last dashboard-side
residue is `ScheduleStatus.svelte`, which fetches `/schedules` on its own 30 s timer outside the
query client (in progress: onto the query client, stream-invalidated).
